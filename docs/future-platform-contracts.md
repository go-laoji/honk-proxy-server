- 日期：2026-11-02（Asia/Shanghai），设计版本 1。

- 实施计划：[future-platform-contracts-plan.md](future-platform-contracts-plan.md)。
- 状态：储备决策与实施准入条件。本文拟议对象和字段尚未进入配置、API、CLI、数据库或 capabilities；不能把它们复制进当前配置使用。当前事实以源码及所链接的已交付使用说明为准，未来实施时重新核查平台/供应商文档。

## 1. 共同边界

首版继续以独立 Rust `hps` / `hpsd`、共享 React/Tailwind MPA、显式 HTTP/HTTPS/SOCKS5、短效供应商与 Linux 自有 eBPF 数据面为基础。T21 不将下面四类能力变成首版隐含承诺，也不把已有的连接档案、配额诊断、规则导入或 DNS 捕获重新命名为这些未来能力。

不增加本项目登录、账号、管理令牌或权限体系。未来编排同样遵守“目标可达即可管理”的产品约定；传输 TLS、供应商凭据、OS 安装权限和签名仍是连接与部署条件。不能通过新增一个控制器暗中引入账号体系，也不能把所有发现到的服务默认加入变更目标。

| 能力 | 当前已存在的基础 | 本任务决定 | 仍未交付的能力 |
| --- | --- | --- | --- |
| FUT-01 | CLI/Desktop 手工连接档案、单实例版本与事件流 | 先做显式登记的目标集合、逐目标结果和单写归属 | 服务发现控制器、配置批量分发、集群/HA 和跨实例会话 |
| FUT-02 | 本地显式代理、远端 Linux 管理、Linux 自有 eBPF | macOS 优先验证 Transparent Proxy；Windows 优先比较签名 TUN 方案，进程感知的 WFP 单独评估 | Mac/Windows 全局接管、平台扩展/驱动及真实恢复验收 |
| FUT-03 | 提取任务、来源预算、快代理 IP 额度诊断 | 先接入可核实的只读口径；金额、配额、估算分开 | 费用账本、供应商账单对账、成本分析与分摊 |
| FUT-04 | 本项目版本化规则、基础选点和真实地址 DNS | 外部规则只转换明确子集；复杂模型与 FakeIP 独立准入 | 外部规则自动更新、表达式/模型评分、目标地址 FakeIP |

T19 / [Issue #24](https://github.com/go-laoji/honk-proxy-server/issues/24) 负责 SOCKS5 UDP、标准订阅、嵌套组和有界高级 Score。T21 不重复交付 T19，也不将其验收推迟到未来：本任务中的“复杂评分”专指超出 T19 固定可解释指标、涉及新公式/模型或费用/跨实例数据的扩展。

## 2. FUT-01：多实例统一编排

### 2.1 产品语义与身份

现有[连接档案](desktop-service-usage.md)只决定客户端当前操作哪个服务，不发现、同步或聚合服务。浏览器随当前 URL 访问一个实例，Desktop/CLI 档案保存 endpoint 和 CA。切换目标会使旧原生请求上下文及事件订阅失效；这不是分布式事务。

当前 [`ServiceStatus.instance_id`](../crates/domain/src/lib.rs) 是 [`AppState`](../crates/api/src/lib.rs) 的运行标识；正常 Daemon 使用 application 的 event epoch，存储打开时生成新的 epoch（[`storage`](../crates/storage/src/lib.rs)）。它会随服务重启变化，不是机器 ID、持久实例身份或可信的设备证明。`instance_name` 和 endpoint 也都不能作为稳定唯一键。

未来对象的拟议契约如下；新增字段时不得改变已有 `instance_id` 和事件 cursor 的含义。

| 拟议对象/字段 | 含义与约束 |
| --- | --- |
| `service_id` | 实例首次初始化时生成并持久化的不透明稳定标识，不来源于主机名、MAC 地址或供应商凭据；克隆数据目录必须显式分配新身份，备份恢复到原实例则保留身份 |
| `runtime_epoch` | 一次服务运行的标识；与当前 event epoch 对齐，用于拒绝旧 cursor、旧连接 ID 和迟到响应，不作为 `service_id` 的替代 |
| `target_id` / endpoint | 控制器登记的目标及其可变地址；同一个 `service_id` 被多个目标地址指向时需显式去重，地址更换不得自动当作新实例 |
| 资源引用 | 聚合层使用 `(service_id, resource_kind, local_id)`；当前 `lease:42`、节点、任务、规则和配置 revision 继续只在各自服务内有效 |
| 发现记录 | 记录来源、最后观测时间和预期身份；发现只生成候选，显式登记后才能参与编排，不广播配置或收集凭据 |

第一轮未来实施选择手工登记目标和按目标检查 version/capabilities/status，不同时引入 mDNS、广播发现、leader election 或共享数据库。自动服务发现如确有需求，须先明确网络范围、身份冲突、过期记录与人工确认语义再扩大这一选择。

### 2.2 状态、配置与节点归属

每个 `hpsd` 仍是自己的 SQLite、供应商调度器、节点池、健康、连接和 OS 对象的唯一写入者；不将一个 SQLite 放到共享目录让多进程写，不共享 eBPF hooks 或代理端口。控制器通过管理 API 调用应用用例，Desktop 仍只负责展示和连接。

“统一编排”第一阶段定义为**一个操作有多个独立目标及逐目标结果**，不承诺全局原子提交。拟议 rollout 记录至少包含操作 ID、目标稳定身份与 epoch、期望的本地 revision、内容摘要、各目标任务 ID、已配置/已激活 revision、阶段与错误。不同实例的 revision 不需要相等；相同数字也不代表内容相同。

分发前检查每个目标的能力、schema/版本和内容适配，生成可审阅差异；分发后仍按目标先准备、再激活、再回读确认。来源 ID、静态节点 ID、路径、证书和设备名需要显式映射；禁止盲目把一台主机的 OS 路径、Linux 对象清单或恢复副本发给另一台。默认分发脱敏业务意图，供应商密钥与私钥的跨机输送不属于这一阶段。

节点、租约和提取批次属于购买/提取它们的实例。聚合相同 IP:port 只能标记可能相同的端点，不能合并有效期、凭据、健康或供应商来源。相同供应商订单由多个实例使用时，当前按来源/UTC 日计数的[补池预算](replenishment-usage.md)不能合并成账户全局预算；启用多实例自动提取前必须选择唯一提取所有者或有可证明排他性的账户级预留机制。否则保留各自服务并明确不承诺全局购买上限。

### 2.3 会话、失败和重试

- 已建立 TCP、TLS、WebSocket 或 UDP 会话留在原实例与原出口；控制器不可迁移现有 socket。实例失联时现有会话按其本地状态结束，客户端重连后才可能进入另一实例。
- 当前会话固定键、租约准入和 TTL 仍是本地语义。未来若需要跨实例出口固定，先证明供应商允许共享租约、统一预算和一致的绑定寿命，再定义独立契约；不因两个实例返回相同节点名称就视为同一会话。
- 单目标 revision 冲突、能力不足或准备失败不覆盖该目标运行版本。连接中断后的结果先标记“未知”，用目标操作/任务标识回查；缺少幂等/结果查询保证时不能自动重发具有提取、断开或网络写入副作用的请求。
- 一部分目标激活成功时整体显示“部分完成”，逐目标给出事实。默认停止后续目标并等待人工选择继续或生成新的补偿意图；不自动回滚已经成功的实例。补偿同样检查其最新 revision，不能覆盖期间的合法改动。
- 聚合事件带稳定服务身份、epoch 和本地 cursor；不得把 A 的任务 ID/cursor 送到 B。切换目标或 epoch 改变时废弃旧请求结果、缓存和订阅，离线目标的数据明确显示最后观测时间。

### 2.4 进入实施的条件与验收

需要一组明确目标、业务配置分发范围、账户提取所有者和故障策略后，才创建有界实施 Issue。至少用两个隔离 Daemon 验收重启、地址变更、克隆身份冲突、同名资源、过期 revision、迟到响应、一个目标失联和部分成功；观测每个本地数据库/运行版本及事件来源。共享订单的提取须另有排他性证据。没有这些证据时仍只提供单实例档案切换，不显示集群 ready、全局预算或跨实例会话。

## 3. FUT-02：macOS / Windows 捕获平台

### 3.1 捕获目标与平台方案

未来功能名称先限定为“该机器上明确范围内的 TCP/UDP 透明代理”。LAN 网关、原始 ICMP、任意 VPN 隧道、流量解密和所有应用绝对覆盖不随该名称进入范围。系统 HTTP/SOCKS 代理设置仍只是由应用选择遵守的显式入口。

以下是方案选择，不是实现或兼容性验证。Linux eBPF 的程序、maps、cgroup 和 ABI 不能在 macOS/Windows 上复用；共享的是 Rust 流量上下文、路由、选点、拨号和观测语义。

| 平台/候选 | 选择及技术前提 | 首次试验必须回答的问题 |
| --- | --- | --- |
| macOS Network Extension Transparent Proxy | 优先验证 `NETransparentProxyProvider` + `NETransparentProxyManager`，以 system extension 承载；本项目先以 macOS 11+ 为候选基线，最终支持版本取实际矩阵 | Rust 接入系统框架、TCP/UDP flow 原始目标、回压、Daemon IPC、系统签名/entitlements、扩展激活与退出后服务生命周期 |
| macOS Packet Tunnel / DNS Proxy | 不用 Packet Tunnel 包装当前选点代理；只有另立真实 VPN 隧道需求才重新评估。系统 DNS 接管单独评估 `NEDNSProxyProvider` 及其部署条件 | Transparent Proxy 不等于 DNS 策略覆盖；如确需系统 DNS，须证明单独 DNS provider 的共存、排除范围与失败语义 |
| Windows 签名 L3 TUN | 优先做 Wintun 候选的可行性比较；从发行方已签名 DLL 接入，Rust 处理包到流的适配和共享引擎调用 | 合法可分发的固定驱动版本、当前 Windows 签名策略、安装权限、IPv4/IPv6 路由、MTU/分片、TCP/UDP 状态、DNS 与回环排除；TUN 本身不提供完整代理或可靠进程来源 |
| Windows WFP connect/bind redirect | 需要进程感知或流级截获时作为独立候选，不与 TUN 首次试验同时承诺交付 | callout 驱动的 Rust 工具链可行性、生产签名/发布、redirect context/records、重复重定向回避、UDP 与其他 WFP 产品共存；不能把一个用户态 socket 重定向示例当作完整驱动 |

Apple 明确将“选中流量后经其他接口代理”的需求导向 Transparent Proxy，而不是 Packet Tunnel。其部署说明区分随用户退出终止的 app extension 与独立于登录用户的 system extension，故后者更符合本项目常驻服务要求。这是基于官方边界的方案判断，Rust/打包路径尚未验证。[Apple TN3120](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers)、[Apple TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)

尤其不能用 Transparent Proxy 的“未处理”返回实现默认拒绝：Apple 说明 `handleNewFlow`/UDP 回调返回 `NO` 会让该 flow 直接到达目标；该 provider 也忽略自己的 DNS/proxy settings，按名称连接仍会先解析。实现必须区分“不在接管范围”与“范围内但出口失败”，后者关闭/拒绝受理的 flow，不能用 `NO` 造成隐式直连。[Apple NETransparentProxyProvider](https://developer.apple.com/documentation/networkextension/netransparentproxyprovider)

Wintun 是包收发适配器；官方提供签名 DLL，并区分源码和预编译包的许可。选用它还需要 Rust 用户态包处理、协议适配及许可评审，不等于采用某个现成的代理后端。[Wintun 官方文档](https://www.wintun.net/)

WFP 由 callout 驱动与代理服务配合；代理端必须保留原目标和 redirect records/context，并避免再次截获自己的出站连接。Windows 驱动能否装载受目标系统签名/Code Integrity 策略约束，“有签名”不能代替当前正式 Windows 镜像实测，也不以关闭安全策略作为发行支持条件。[Microsoft WFP redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection)、[Windows Driver Policy](https://support.microsoft.com/en-us/windows/hardware/drivers/the-windows-driver-policy)

项目自己的业务、特权控制及数据适配仍用 Rust。macOS 框架 FFI/extension 入口和 Windows 驱动接入均须先通过工具链与签名试验；不能因系统 SDK 示例是 Swift/C++ 就额外引入另一套业务后端。若 Rust 约束或分发条件不成立，则保留显式代理并报告平台透明能力不可用，先提交决策再扩大语言/依赖范围。

### 3.2 与共享引擎的兼容契约

拟议捕获适配器负责：返回平台、模式、scope、原始源/目标、传输、地址族、经过验证的可选进程来源、对象归属、资源上限和本地配置代际；提交用户态统一路由后再拨号。provider、驱动或辅助进程不自行同步供应商、写 SQLite 或维护第二套选点/健康状态。若 OS 要求扩展进程承载 flow，使用有界 IPC 与 Daemon 协作，Daemon 仍是唯一业务所有者。

当前 [`RoutingContext` / `FlowOrigin` / `ProcessIdentity`](../crates/domain/src/routing.rs) 的 origin 是 `explicit` / `linux_local` / `gateway`，进程结构含 Linux `cgroup_id`。未来平台不能伪装成 `linux_local`、凭空填 PID/cgroup 或将未知进程匹配为成功。新增来源和平台进程结构须有显式 schema/版本与客户端兼容决策；不支持的过程条件在准备时拒绝，而不是静默变成通配。网关客户端也不会获得本机进程身份。

未来 capability 至少区分 compiled、平台/安装前提、configured、attached、ready、TCP/UDP、地址族、DNS 覆盖、进程来源与失败策略；这些是需要设计的新契约，不是当前 [`Capabilities`](../crates/domain/src/lib.rs) 已有字段。ready 必须来自服务实际状态和验证结果。macOS Desktop 连接 Linux Daemon 时继续展示目标 Linux 能力；本地 OS 不决定远端能力。

不在范围的流量可以遵循系统原行为；被明确接管且要求代理的流量在无节点、额度耗尽或 IPC 失败时不得自动变为直连。驱动/扩展崩溃、卸载和 OS 强制终止是否仍可阻止直连，必须单独实测并披露；在未证明前不宣传持久 kill switch。显式停止接管是另一种操作意图，按精确对象归属释放本实例资源，不自动套用旧系统配置。

### 3.3 进入实施的条件与验收

每个平台单独选定支持 OS/架构、合法签名/发行路径、Rust 接入、捕获范围和 DNS/故障策略后再拆实施 Issue。Apple 账号/entitlements、Windows 签名驱动及 OS 安装确认不属于本项目账号验证。

真实网络写入验收只在确认隔离的虚拟机及独立测试接口内执行，记录镜像、架构、OS 构建、驱动/扩展摘要、对象所有者与前后网络状态。至少覆盖双栈 TCP/UDP、无 UDP 上游、DNS 名称/IP 连接、第三方 VPN/代理共存、回环与供应商/健康/管理流量排除、睡眠唤醒、网络切换、故障、SIGKILL/重启、升级和卸载；平台不支持的维度明确不可用。验收不能只证明编译、UI 开关或 mock。

开发宿主 Mac 不进行 Wi-Fi、DNS、路由或系统代理写入；不运行已作废的旧网络测试二进制。开发 Desktop 必须设置 `HPS_FORBID_HOST_NETWORK_CHANGES=1`；宿主仅允许只读诊断和无 OS 写入的事务/恢复检查。T21 本次不启动任何捕获或开发应用。

## 4. FUT-03：供应商成本、计费与分析

### 4.1 当前事实与真实供应商口径

当前 [`ProviderClient::diagnostic`](../crates/provider/src/lib.rs) 对快代理 `quota` 调用 `/api/getipbalance`，输出 `unit="ips"`，不是金额；通用/免费来源缺少诊断契约时返回 unsupported/unknown。当前提取任务和本地预算记录请求/预留/不确定结果，不能据此证明供应商实际扣费或账单。

| 第一方信息 | 已核实的含义 | 对未来实现的约束 |
| --- | --- | --- |
| 快代理订单 `getipbalance` | 对按 IP 付费订单返回剩余 IP 提取额度；对包年包月集中提取型返回今日剩余额度 | 同为 `balance` 仍有不同周期；须取得订单类型与周期，不能只凭数值汇总或相减推算消费金额 |
| 快代理 Gateway `GET /v1/account/funds` | 账户现金余额、可开票金额、币种，可有 `as_of`；与订单提取 API 使用不同凭据/接口 | 现金余额不是某实例消费、可开票金额不是支出，也不是逐笔计费明细；当前适配器没有接入该 Gateway |
| Gateway 订单详情 `quota_items` | 指标、单位、total/used/remaining 与 reset_period | IP、bytes 等不同单位和周期不得相加；不提供的时间或维度保持未知 |
| Gateway 订单统计 | 官方描述为最近 24 小时摘要，有产品不支持的情况 | 不能宣称任意历史账单、完整请求时间序列或代理目标归因已可获取 |

依据：[快代理订单 IP 提取余额](https://www.kuaidaili.cn/doc/api/getipbalance/)、[快代理 Gateway API 接入指南](https://www.kuaidaili.cn/doc/using/cli_api_guide/)。截至本次仅查阅公开文档，没有调用账户、额度、购买或收费接口。没有取得本项目实际订单/授权凭据、真实对账单或价格合同；这些仍是成本功能实施和验收的前提。

### 4.2 拟议归一化契约

| 对象 | 必须表达的信息 |
| --- | --- |
| 配额观测 | 供应商、脱敏订单/计费范围引用、metric/unit、total/used/remaining 可空值、周期/重置时区、供应商 `as_of` 与本地接收时间、数据来源和精度 |
| 金额观测 | 同样的计费范围与时间；金额用定点十进制字符串及币种，不用浮点；现金/报价/实际支出/退款分开，不自动换汇 |
| 计费事件 | 供应商事件/账单行标识、发生/结算时间、计费口径版本、数量和单位、金额/币种、关联订单/提取批次及证据状态；没有唯一标识的聚合快照不伪造成逐笔事件 |
| 本地估算 | 公式/费率版本、有效日期、计费粒度、税费/包月摊销假设、输入数量和覆盖时间；标记 estimated，缺少输入时 unknown，不用零值补齐 |
| 数据质量 | confirmed / estimated / unknown / unsupported，最后成功观测、刷新错误、允许新鲜度与覆盖缺口；错误不覆盖旧事实，但旧事实明确 stale |

计费范围是供应商外部订单或凭据的业务归属，不是本项目用户。多个来源、实例指向同一订单时，快照按供应商/范围/metric/周期去重，事件按供应商稳定事件标识去重；重新抓取不重复入账，退款/更正保留关联原事件的调整记录。禁止把各实例观测到的相同账户余额相加。

只有供应商确认的口径才能定义“成功一次提取是否收费、重复 IP 是否计费、重试/响应丢失是否收费、探测流量是否计量、流量以哪个方向/单位计量”。本地接收节点数、连接字节和健康探测计数只作业务观测；不替代供应商计量，不把请求失败当作免费。

当前本地预算按来源 ID、UTC 日保守预留；供应商额度可能按 Asia/Shanghai 自然日或订单总量重置。保留各自时间语义，展示时标注边界，不改动现有预算来假装同步供应商账目。提取结果 `outcome_unknown` 不自动重试、不自动冲回成本；具备供应商请求查询/幂等保证后才对账解除不确定状态。

初次成本扩展只读，不自动购买、充值、续费、改白名单或更新支付资料；这些操作需要独立产品意图与验收。供应商 Gateway 所需外部凭据与当前订单凭据分开保管，日志/导出只含脱敏引用，不能把外部 Bearer 认证变成本项目管理认证。

### 4.3 进入实施的条件与验收

先提供实际采用供应商和产品的官方 API/版本、订单类型、计费合同/费率、单位/周期、只读授权、脱敏真实成功/错误/缺字段样本，以及账单或人工确认口径。没有逐笔账单时可以明确限定为“额度与余额看板”，不能将其命名为已完成实际成本对账。

验收应将同一订单的真实观测与脱敏账单核对，覆盖共享账户、跨日/跨时区、重复页/乱序事件、超时不确定、退款、更正、过期数据、无金额及无支持 API。展示支出只统计 confirmed，estimated 单列，unknown 显示缺口。凭据/订单隐私不提交仓库或 Issue；证据仅保留必要脱敏字段和对账结果。没有真实供应商证据时只验收归一化设计，不宣称成本已验证。

## 5. FUT-04：外部规则、复杂评分和 FakeIP

### 5.1 外部规则集的转换与更新

当前本项目 [`RuleDocument`](../crates/config/src/routing.rs) 和[规则导入](routing-rules-usage.md)有自己的版本、规则动作、checksum 和 `expected_revision`；它们不是第三方配置解释器。供应商的标准节点订阅属于 T19，与路由规则订阅分开建模。

格式不能只凭文件扩展名判断兼容：sing-box 区分 source/binary rule-set 与 headless rules；mihomo 另有 domain/ipcidr/classical behavior 和 yaml/text/mrs format。未来实现固定到明确上游版本及支持子集，独立编写 Rust 解析/转换器，不引入 honk/sing-box/mihomo 运行时或代码依赖。[sing-box 官方规则集](https://sing-box.sagernet.org/configuration/rule-set/)、[mihomo 官方规则集合](https://wiki.metacubex.one/config/rule-providers/)

第一轮外部规则候选仅转换明确版本的纯域名、按标签边界的域名后缀和 IPv4/IPv6 CIDR；动作由用户在本地绑定。若上游列表含动作、逻辑组合、正则、脚本、进程、Geo 数据或隐式 DNS/resolve 行为，整批拒绝并报告条目/原因，不能静默丢弃后宣称完全兼容。IDN、大小写、尾点、根域匹配、通配符、CIDR 正规化、顺序/优先级和重复项语义须有与固定版本来源相符的真值案例。二进制 SRS/MRS、GeoIP/Geosite、自动解压和任意脚本不属于这一轮。

拟议来源记录包含来源 ID、明确格式与语义版本、用户绑定的本地动作/优先级、下载出口与 bootstrap、抓取预算、许可证/分发条件、最后成功摘要/版本/时间、有效期及本地激活 revision。导入结果记录原条目到本地规则的映射，模拟和真实决策能解释来源与激活摘要；第三方不能通过规则内容覆盖供应商、监听或系统设置。

更新事务定义为：

1. 仅按用户登记的来源抓取，经 TLS 校验并限制重定向、响应/解压大小、条目数量、解析深度、并发及超时。下载路径由本项目生成且局限私有缓存；不执行内容、不接受内容中的任意本地路径，跨域重定向不携带凭据。
2. 先用固定格式解析、校验语义/引用/资源预算及版本；校验用户固定的摘要，或验证独立受信密钥签名。下载正文附带的 SHA256 只能检测传输/缓存变化，不自动证明来源可信；ETag 不作为版本顺序或可信签名。
3. 形成独立候选与差异，按本地 `expected_revision` 准备并发布；外部更新不能覆盖并发人工编辑。相同来源任务携带序号，较早或迟到结果不得替换较新候选；有签名序号/到期字段时验证防回退，旧版本重用须形成明确回滚意图。
4. 用户态/内核发布都成功并回读后才记为 active；抓取、解析、引用或发布失败保留上一有效版本，显示失败阶段、陈旧时间与摘要。304 只验证已有完整缓存，不能从缺失/损坏缓存恢复成功。
5. 空集和大幅缩减作为需审阅的配置意图；首次无缓存则来源 unavailable。已过有效期的来源不能无限隐藏在“刷新失败保留旧版本”中：到期前告警，到期后按预先声明的策略拒绝依赖该来源的新连接，不能移除规则而意外放行。

进入实施前选定一个来源格式/版本、允许分发的数据与许可证、更新信任/密钥方式、下载出口和失效策略。验收覆盖黄金样例、未知操作符、恶意 YAML/路径/压缩、损坏签名、回退版本、304 无缓存、空集、超大集、断网、并发编辑和用户态/内核发布失败；检查旧版本仍可解释且不会意外变更放行范围。HTTP 下载成功不等于规则已生效。

### 5.2 超出 T19 的复杂评分

不改变现有 fixed、failover、latency、round_robin、weighted 及 T19 有界高级 Score 的语义。后续复杂评分可能涉及可配置公式、多目标模型、成本或跨实例指标；只有具备实际新需求、可核实的输入与预算时才另立实施范围，当前不预埋表达式执行器或模型下载器。

拟议模型契约必须记录模型/公式版本、目标、输入指标定义/单位/采样范围、观测窗口与新鲜度、最小样本、归一化、权重/上下限、缺失值和并列决策。每次模拟/真实决策能解释候选被淘汰的硬条件、各分项输入/贡献、最终顺序及所用版本；费用未确认、UDP 无证据或跨实例样本不可比较时，不能编造低成本或高质量分数。

评分只作用于已经通过启停、租约寿命、协议/地址族、来源/地域、健康和用户固定/回退范围的候选，不能让高分越过硬性约束。数据过期或资源预算耗尽时，使用用户明示且兼容的现有策略或拒绝；不隐式扩大候选、购买节点或切换直连。模拟不推进轮询、不建立绑定、不探测/提取；新模型只影响新连接，既有会话和出口不迁移。

进入实施前需有脱敏输入集、期望真值、成本/精度目标和资源预算。验收同一输入与模型版本得到可重放结果，拒绝非有限数/溢出/越界公式，覆盖缺失/过期样本、并列、时钟变化与性能上限，先影子比较再显式激活。若含任意表达式或外部模型，需在该实施 Issue 定义沙箱、执行/内存上限、来源完整性与失败方式；不能用“高级 Score 已存在”替代这些证据。

### 5.3 FakeIP 的 DNS 与路由契约

当前 DNS 返回真实上游结果，并维护有来源和 TTL 的观测；同一真实 IP 对应多个域名时返回多个候选或未知。[Linux DNS 捕获](dns-usage.md)中的 `127.77.0.0/16` / `fd77:6870:7300::/112` 只保存客户端原 DNS 对端身份，不是业务目标 FakeIP，也不能直接复用为目标地址池。

未来 FakeIP 定义为：对进入本实例受控 DNS 的业务 A/AAAA 查询分配本实例持有的合成地址，后续流量必须在相同映射域内还原原始域名并进入统一规则/选点。它不解密 TLS，不恢复未观测域名；外部 DoH/DoT、硬编码 IP、绕过该 DNS 的应用不保证适用。

| 兼容面 | 拟议要求 |
| --- | --- |
| 地址池与范围 | IPv4/IPv6 分别选择可路由捕获且不与真实 LAN/VPN、DNS alias、管理/上游/健康地址冲突的池；不能因为某地址段常被其他软件使用就假定可用。上线前真实检查冲突，所有合成地址禁止当成真实目标直连 |
| 映射身份 | 至少按实例/映射域、规范化域名、地址族、DNS 策略代际隔离；业务解析可用，bootstrap/provider/health/管理解析明确排除以免循环 |
| TTL、容量与复用 | 有界分配、反查和持久格式；地址不得在客户端可能仍缓存或存在活跃会话时复用给另一域名。先公布最大 TTL、会话排空/保留窗口与重启恢复契约；容量不足显式失败，不随机覆盖或无提示返回真实 IP |
| 路由与选点 | 先恢复域名后按同一规则、硬性准入和连接固定语义执行；说明 IP/CIDR 规则匹配原始地址还是经所选 DNS 策略解析的真实地址。默认不对合成地址匹配真实地域/CIDR，不能为满足规则隐式改变远端解析语义 |
| DNS 兼容 | 逐项定义 A/AAAA、CNAME、负缓存、DNSSEC/AD、PTR、HTTPS/SVCB 与其他 RR：合成答案不能声称是经 DNSSEC 验证的原始答案（[RFC 4035 AD 语义](https://www.rfc-editor.org/rfc/rfc4035.html#section-3.2.3)）。不承诺未实现记录可转换；内部/局域网和显式排除域按声明的真实解析策略处理 |
| 热更新/重启 | 先准备映射与捕获再发布 DNS 答案，失败保留上一一致代际。规则/DNS 热更新、缓存清理、停用和崩溃重启不能让客户端缓存中的旧合成地址误连到其他域名；无法恢复映射时拒绝该地址并明确要求客户端重新解析 |
| 多实例 | 地址不作为跨实例全局身份；在 A 获取的合成地址若可能由 B 捕获，必须先证明共享映射/一致路由与隔离语义，否则禁止该拓扑 |

DNS、捕获和映射存储必须作为同一实施范围验收；仅在 DNS 响应里返回一段合成 IP 不能通过。进入实施前选择具体部署范围、地址池、真实/合成解析切换、映射恢复方式和 RR 支持矩阵，并明确直接 IP、应用自带 DoH/DoT 与远端 SOCKS 域名解析的体验。

真实隔离环境至少验收 A/AAAA/CNAME、同名跨策略、容量耗尽、冲突地址、旧缓存跨热更新/禁用/重启、活跃会话地址保留、合成 IP 未知映射拒绝、IPv4/IPv6 规则、DNSSEC/AD 和 HTTPS/SVCB 边界；同时观测发往上游/网络的真实目标，证明合成地址没有泄露成直连目标或串域名。宿主 Mac 禁写约束同 FUT-02。
